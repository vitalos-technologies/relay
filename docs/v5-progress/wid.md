## Decisions
- **No second ticket system.** A widget conversation is a V4 `support_tickets` row with `source='widget'`; visitors use
  `requester_kind='visitor'` + `visitor_id`, signed-in customers `requester_kind='member'` via `insertMemberTicket()` /
  `replyTicket()` (V4 visibility rules, rate-limit buckets and idempotency reused).
- **Visitor identity** = `widget_visitors.id` (random uuid from the DB, never derived from input, never sent to the browser).
  Browser holds an opaque 32-byte token in an HttpOnly cookie (`relay_widget`; `__Host-relay_widget` + Secure in
  production; SameSite=Lax); only SHA-256 stored (`widget_sessions`). 30-day absolute, 7-day idle; "End chat on this device".
  Own CSRF token per visitor session (`X-Widget-CSRF`); member mutations use the app session CSRF (`X-CSRF-Token`); all
  mutations need same Origin + `X-Relay-Widget: 1`. An identity whose CSRF header is absent is ignored for that request.
- **Email never proves identity.** Visitor sees tickets of its own identity, plus — only after the one-time verification —
  tickets whose contact email equals the session's *verified* email. Verification: 6-digit code (5 tries, then locked) or
  one-time link, 15 min; emailed only when the address has widget conversations (same API answer either way). Secrets are
  generated by the worker at send time; only hashes stored. Links use the URL fragment `/#support-verify=…` (never sent to
  the server on load; scanners can't consume it; the widget asks for a click, then POSTs). No account/workspace merge ever.
- **Staff reply → visitor:** shows in the widget (cursor polling) + content-free "Relay support replied · RLY-…" email with a
  one-time 72 h link (`widget_emails`, dedupe `support:msg:<id>`, outcome shown under the reply in Platform → Support;
  `not_configured` without SMTP). Member widget tickets keep the V4 in-app/email notifications (→ Help → My requests).
- **Internal notes** never reach the widget: widget reads only `support_messages` + customer-audience activity; note
  attachments are 404 through `/api/widget/attachments`; verified by tests over reads, deltas, session list, reply payloads
  and emails.
- **Live updates:** polling `GET /api/widget/conversations/:ref?after=<cursor>` (cursor = customer-audience
  `support_activity.id`). Every message writer locks the ticket row before appending activity, so per-ticket ids become
  visible in commit order → "id > cursor" never skips (no overlap window needed). No SSE; no typing/read indicators.
- **Availability:** `marketingConfig()` (MKT, `system_flags.marketing_config`): `widget_enabled` (default **off** — MKT
  default), `widget_staffed` → title "Chat with Relay support", else "Send us a message". No online dot, no response times.
  Email is promised in copy only when SMTP is configured (`availability.email_replies`).
- **Abuse controls:** shared Postgres buckets — create 10/h per IP + 5/h per visitor; reply 30/10 min per visitor + 60/10 min
  per IP; reads 600/10 min per IP; attachments 20/10 min per IP + V4 per-owner bucket; verify 5/h per IP + 3/h per email;
  confirm 20/h per IP. Honeypot field, HMAC-signed time-trap form token (≥1.5 s, ≤6 h), visitor message ≤ 4000 chars,
  JSON ≤ 64 KB, staff **Block visitor** (ends sessions; audited).
- **Category `general`** ("General question") added (contract + 037 constraint) for pre-sales questions.
- **Attachments:** V4 quarantine pipeline; `support_attachments.visitor_id` for visitor-owned uploads. Visitors can attach
  once their first message created a session (reply composer / later messages).
- **Diagnostics (minimal):** page path (no query/fragment), browser family, time. Nothing else.
- **Lazy loading:** only `launcher.tsx` (inline SVG, no icon/dialog libs, no fetch on load) is in the page bundle; the
  panel chunk loads on click/hover/focus/`#support`/`relay:open-support` or after `requestIdleCallback` (timeout 8 s,
  after `load`). Launcher steps aside (hidden, unfocusable) while overlapping `#pricing a/button`,
  `[data-support-widget-avoid]`, `[data-cookie-controls]`.
- **Mobile:** ui-v5 Sheet (Base UI dialog) full-screen with "Close chat"; height follows `visualViewport` so the composer
  stays above the on-screen keyboard; desktop floating 25 rem panel.
