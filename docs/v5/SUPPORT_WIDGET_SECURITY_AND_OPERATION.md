# Support widget — security and operation (V5)

The marketing-page chat launcher lets visitors and signed-in customers write to Relay staff. It is a thin client of the
existing **Platform → Support** service (V4): every widget conversation is an ordinary support ticket with
`source = 'widget'`. There is no second ticket system, inbox or notification path. This is communication with Relay
staff — it never touches a customer's social inbox.

Code: `packages/services/src/support/widget*.ts`, `apps/web/app/api/widget/**`, `apps/web/components/support-widget/**`.
Schema: `packages/db/migrations/037_v5_widget.sql`. Contract: `packages/core/src/contracts/v5-widget.ts`.

## Turning it on
Admin → Platform → **Marketing** (operators, fresh MFA, audited):
- **Support widget on** (`widget_enabled`, default off). While off, the launcher is hidden for new visitors and new
  conversations are refused; browsers that already have a conversation (or open a one-time link) still see their replies.
- **Staffed live chat** (`widget_staffed`) — only when people actually watch the support inbox. Changes the title from
  "Send us a message" to "Chat with Relay support". The widget never shows an online status, response time, typing or read
  indicator (no real events back them for visitors).
- **Privacy link** (`privacy_url`) is linked from the widget's privacy note when set.

## Who can see what

| Caller | Sees | How it is decided |
|---|---|---|
| Visitor (this browser) | Conversations started by this browser's visitor identity | `widget_sessions` cookie → `visitor_id` |
| Visitor after email verification | + conversations whose contact email equals the **verified** email | one-time code / link (below) |
| Another visitor (any browser, even one that types the same email) | Nothing — 404 | no session for that identity, email not verified |
| Signed-in customer | Their own requests in a workspace they belong to (V4 rules) | app session + `loadAccess` for the chosen workspace |
| Relay staff (support / operator) | Everything, incl. internal notes | V4 `requireSupportStaff` |

- **Visitor identity** is a random uuid created by the database. It never leaves the server and is never derived from the
  name or email typed. The browser holds only an opaque 32-byte token in an **HttpOnly** cookie (`relay_widget`; in
  production `__Host-relay_widget`, Secure); the server stores its SHA-256. SameSite=Lax.
- **Session lifetime:** 30 days absolute, 7 days idle; "End chat on this device" revokes it at once. Expired/ended sessions
  are deleted after 30 days (worker). Conversations stay; reopening them needs the email code.
- **Email never proves identity.** It is stored as typed ("not verified" for staff) and used only as the reply address.
  It grants nothing until verified, and **visitor conversations are never merged into a user account or workspace** — not
  even when the email matches a Relay user. Signed-in customers always write as themselves (`requester_kind = 'member'`).
- **Workspace (signed-in):** the widget offers the user's active workspaces; the server re-validates membership of the chosen
  workspace on every call. A workspace id the user doesn't belong to is refused.

## Cross-device access (verification)
1. "Continue from another device" → enter the email used. The API always answers the same (202); a code is emailed
   **only** if that address has widget conversations — the widget can't be used to send mail to arbitrary inboxes or to
   discover who wrote to Relay.
2. The email contains a **6-digit code** and a **one-time link**, both valid 15 minutes. The code allows 5 tries, then locks.
   Secrets are generated by the worker at send time; only hashes are stored (never in the outbox, logs or database as plain text).
3. The link is `https://…/#support-verify=<token>`: the token is in the URL fragment, so it is not sent to the server when
   the page loads and not leaked in Referer headers; mail scanners that prefetch the link consume nothing. The widget removes
   it from the address bar and asks the person to press **Continue** before it is used.
4. Success marks **this browser session** as verified for that email (and records "verified" for staff). Nothing else.

## Messages, replies and notifications
- New conversation → ticket (`new`, category from the topic; "General question" by default) + staff notification
  (`support.new`, platform scope) through the outbox → worker → notifications pipeline.
- Visitor reply → `waiting_on_relay` (reopens a resolved conversation within 30 days) + notification to the assignee (or all
  support staff when unassigned). Staff first reply auto-assigns, as in V4.
- Staff **public** reply → appears in the widget (polling) and the contact address receives a content-free email
  "Relay support replied · RLY-…" with a one-time 72-hour link to the conversation. One email per staff message
  (deduplicated); the outcome — emailed / queued / not configured / failed — shows under the reply in Platform → Support.
  Member widget conversations keep the V4 in-app + email notifications linking to Help → My requests.
- **Internal notes never reach the widget**: the widget reads only `support_messages` and customer-audience activity; note
  files are 404 through `/api/widget/attachments`; emails carry no message text. Covered by integration tests over full
  reads, polling deltas, the session list, reply responses and emails, and by E2E.

## Reliability
- **Deduplicated submission:** every message carries a client-generated id. A retry (double click, flaky network, lost
  response) returns the original message; the same id with different content is refused. A first message whose response
  was lost gets a fresh session for the same identity on retry (the id is a 122-bit secret only that browser had).
- **Reconnect + missed messages:** the widget polls `GET /api/widget/conversations/:ref?after=<cursor>` every 5 s while open
  and visible (backs off to 60 s on errors, pauses in hidden tabs, retries at once when the browser comes back online). The
  cursor is the customer-audience activity id; writers lock the ticket row first, so nothing published while offline is
  skipped. The client also dedupes by message id.
- **States:** loading, offline banner, "Reconnecting…", per-message "Sending… / Not sent · Retry · Remove", load errors with
  Try again, closed/resolved notices.
- **Attachments:** the V4 private pipeline (presigned upload to the private bucket, quarantine, server-side type/size/
  signature check, authorized download re-checked per request). Visitors can attach once their first message created a
  session. Images, PDF, text; 10 MB; 5 per message.
- **Diagnostics (minimal, automatic):** page path without query/fragment, browser family, time. Nothing else (no IP, no full
  user agent, no device data).

## Abuse controls
| Control | Limit |
|---|---|
| New conversations | 10 / hour per IP, 5 / hour per visitor |
| Replies | 30 / 10 min per visitor, 60 / 10 min per IP (members: V4 per-person limits) |
| Conversation reads (polling) | 600 / 10 min per IP |
| Uploads | 20 / 10 min per IP + 20 / 10 min per owner |
| Code requests | 5 / hour per IP, 3 / hour per email |
| Code / link confirmations | 20 / hour per IP; 5 tries per code |
| Size caps | visitor message 4 000 characters, request body 64 KB, name 120, email 254 |
| Bots | hidden honeypot field; HMAC-signed form token (time trap: ≥ 1.5 s, ≤ 6 h) |
| CSRF | same Origin + `X-Relay-Widget` header on every mutation; visitor CSRF token per session; member mutations use the app session token |
| Staff | **Block visitor** (ticket → Actions): ends the visitor's sessions and refuses new messages; audited |

Limits use the shared PostgreSQL buckets (hold across web replicas). Client IP is the first X-Forwarded-For hop — set up
the proxy as described in `DEPLOYMENT.md`.

## Performance and accessibility
- Only the launcher (a button with an inline icon, no dialog or icon library, no request on load) is in the marketing
  page's JavaScript. The panel is a separate chunk loaded after the page is idle or on first interaction (click, hover,
  focus, `#support` link, `relay:open-support` event). Measured (production build): launcher ≈ 2.0 KB gzip in the page chunk; panel chunk 10.0 KB gzip, not in the initial load; cold click → dialog ≈ 150 ms (details in `docs/v5-progress/wid.md` § Performance).
- The panel is an accessible dialog (Base UI via `components/ui-v5/sheet`): labelled by its title, focus trapped and
  returned to the launcher, Esc and a labelled **Close chat** button. Fields have labels and announced errors; new staff
  replies are announced politely; motion respects reduced-motion.
- Phones: a full-screen sheet whose height follows the visual viewport, so the reply box stays above the on-screen keyboard.
  The launcher steps aside while it would overlap pricing actions, cookie controls (`[data-cookie-controls]`) or any element
  marked `data-support-widget-avoid`; footer `#support` links still open it.

## Privacy note shown to visitors
"We use your name, email and messages to reply, plus the page you're on and your browser type. A cookie keeps this
conversation in this browser for up to 30 days. Conversations are kept for up to two years after they're closed."
(V4 retention: resolved → archived after 30 days → purged 730 days after archive.) This describes behaviour; it is not a
legal compliance statement.

## Operating notes
- Staff find widget conversations with the **Source → Marketing widget** filter or the "Widget" badge; search covers the
  visitor's contact email.
- Visitor facts on a ticket: name (visitor), email (verified / not verified), "not linked to an account", active chat
  sessions and other conversations from the same browser identity.
- Without SMTP: replies still appear in the widget; staff see "email not configured"; the widget does not promise email and
  hides "Continue from another device".
- Worker (`support-sweeps`, every 60 s): visitor email retries (3 attempts with back-off), verification expiry/cleanup,
  ended-session and orphan-visitor cleanup.

## Activation
- SMTP sender (visitor reply emails and verification codes).
- Turn the widget on in Platform → Marketing; mark staffed only when the inbox is watched.
- `SESSION_SECRET` (production; signs the form token).
- Attachment malware scanning remains a V4 gap (validation-only quarantine).
